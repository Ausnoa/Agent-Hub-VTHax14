# Decision 006: Prisma integration scope

## Context

The hosted (Supabase) path already has a complete, working, tested multi-user
persistence layer before Prisma was introduced:

- Schema and Row Level Security live in hand-written SQL migrations
  (`supabase/migrations/202609190001_hosted_agents.sql`,
  `...0002_hosted_workflows.sql`, `...0003_profiles_and_visibility.sql`),
  covering `template_agents`, `agent_test_runs`, `agent_test_budgets`,
  `hosted_workflows`, `hosted_workflow_runs`, `hosted_workflow_budgets`,
  `profiles`, and `saved_agents`.
- Authorization is enforced by Postgres RLS keyed on `auth.uid()`, exercised
  by every hosted API route through a per-request `supabase-js` client
  scoped to the caller's Bearer token (`src/lib/hosted/server.ts::authenticate`).
  Several `SECURITY DEFINER` functions (`reserve_agent_test`,
  `reserve_workflow_budget`, `start_hosted_workflow`, `claim_hosted_step`,
  `finish_hosted_step`) and a trigger (`handle_new_user`) implement atomic
  budgeting, idempotent run creation, and step claiming.
- This is covered by tests (`tests/hosted-*.test.ts`) that run the real
  migration SQL against an embedded Postgres (`@electric-sql/pglite`) and
  assert RLS actually blocks cross-owner access.

Prisma's connection model queries through one fixed DB credential. It does
not natively carry a per-request user's JWT the way the existing
`supabase-js` client does, so using it as a drop-in replacement for the
existing repository code would either bypass RLS (requiring every
authorization check to be re-implemented by hand in application code) or
require wrapping every query in a transaction that injects
`request.jwt.claims` to keep RLS active through Prisma. Both are real
rewrites of code that already works and is already tested.

## Decision

Prisma was added **additively**: for schema-as-code, introspection tooling,
and generated types, not as a replacement for the existing data access
layer.

- `prisma/schema.prisma` is generated by introspecting the live database
  (`npx prisma db pull`) — it documents the schema, it does not define it.
- `supabase/migrations/*.sql` remains the single source of truth for schema
  changes. Prisma does not own migrations here (`prisma migrate` is not
  used, to avoid a shadow-database/migration-history that would compete with
  the existing hand-written SQL files).
- None of the existing hosted repository code
  (`src/lib/hosted/{server,workflow-store,profile,saved,discover}.ts`) or
  API routes were changed. They continue to use `supabase-js` with the
  caller's Bearer token, so RLS continues to be the authorization boundary
  it already is.

Verified: `npm run typecheck` and `npm test` (80/80, including the pglite
RLS migration tests) pass unchanged after this integration, and a live
read query through the generated Prisma Client against `profiles` returned
real rows — see "Verification" below.

## Prisma 7 specifics (discovered while wiring this up)

Prisma 7 changed enough that it's worth recording exactly what this
integration does, beyond the "classic" Prisma mental model:

- **`npm`'s `latest` tag for `prisma` currently resolves to a `8.0.0-rc.15`
  prerelease** that pulls in an unrelated cloud-provisioning toolchain
  (`@prisma/composer`, `alchemy` with AWS/Cloudflare providers) and doesn't
  match `@prisma/client`'s stable line. Both `prisma` and `@prisma/client`
  are pinned to `^7.10.0` (the `prev` dist-tag) in `package.json` — do not
  `npm install prisma@latest` without checking dist-tags first.
- **Connection URLs no longer live in `schema.prisma`.** They live in
  `prisma.config.ts` (project root), which the Prisma CLI loads for
  `db pull`/`generate`. This file does **not** auto-load `.env` — it
  explicitly does `import "dotenv/config"`, which is why `dotenv` is now a
  devDependency.
- **`DIRECT_URL` uses the Session Pooler, not the literal "Direct
  connection" string from the Supabase dashboard.** Supabase's direct host
  (`db.<ref>.supabase.co:5432`) resolves IPv6-only unless the project has
  the IPv4 add-on, and many networks (including the one this was built on)
  have no outbound IPv6. The Session Pooler
  (`aws-0-<region>.pooler.supabase.com:5432`, username
  `postgres.<project-ref>`) is IPv4-reachable and supports the
  session-level features introspection needs, unlike the Transaction
  Pooler (port 6543). `DATABASE_URL` uses the Transaction Pooler (6543) as
  originally planned, for runtime query traffic.
- **Introspection needs the `auth` schema to resolve foreign keys.** Every
  `public` table's `owner_id`/`user_id` references `auth.users`. Without
  `schemas = ["public", "auth"]` in the `datasource` block, `prisma db pull`
  fails with `P4002` (cross-schema reference not allowed). The tradeoff:
  `prisma/schema.prisma` now also contains ~25 models mirroring Supabase's
  internal GoTrue (`auth.*`) schema. This is the same pattern Supabase's own
  Prisma docs recommend. **These `auth.*` models are read-only
  documentation of a schema Prisma does not own** — they exist solely so
  the `public` tables' relations resolve, and must never be targeted by a
  migration or write. `schema.prisma` is regenerated wholesale by
  `db pull`, so hand-written comments in it (including the scope note at
  the top) do not survive a refresh; this file is the source of truth for
  that.
- **`PrismaClient` now requires an explicit driver adapter** — it can no
  longer read a connection URL from the environment/schema on its own.
  `@prisma/adapter-pg` and `pg` were added as runtime dependencies for
  this. Any future code using Prisma Client must construct it like:
  ```ts
  import { PrismaClient } from '@prisma/client';
  import { PrismaPg } from '@prisma/adapter-pg';

  const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
  const prisma = new PrismaClient({ adapter });
  ```
- **Known, unaddressed `npm audit` findings**: `prisma`'s own dependency
  tree (`@prisma/config` -> `deepmerge-ts`, and a bundled `mysql2` we never
  use) currently has 4 high-severity advisories. They're transitive to the
  CLI devDependency, not the runtime `@prisma/client`/`@prisma/adapter-pg`
  path, and `npm audit fix --force` would downgrade to `prisma@6.19.3`,
  reverting the config/adapter architecture this doc describes. Left
  as-is; revisit when Prisma ships a patched `7.x`.

## Workflow for future schema changes

1. Write the change as a new file in `supabase/migrations/`, including RLS
   policies/grants, following the existing migrations' conventions.
2. Apply it to the Supabase project (SQL Editor, as documented in
   `docs/HOSTED-BUILDER.md`).
3. Run `npx prisma db pull` to refresh `prisma/schema.prisma` from the live
   schema, then `npx prisma generate` to rebuild the client.

## Using Prisma Client

Prisma Client's connection (`DATABASE_URL`, via the `pg` driver adapter) is
a pooled Postgres credential and **bypasses RLS**. It must not be used to
serve user-owned data (agents, profiles, saved agents, runs) without
re-deriving the equivalent authorization checks by hand in application
code — at which point you no longer get RLS's guarantee that a missed
`where` clause fails closed. Until there's a concrete need that the
RLS-scoped `supabase-js` client can't serve (e.g. trusted, non-user-scoped
server tooling), new hosted-data code paths should keep using the existing
`src/lib/hosted/server.ts` pattern rather than Prisma Client.

## Environment variables

Two new server-only variables (never `NEXT_PUBLIC_`), from the Supabase
dashboard under Project Settings -> Database -> Connection string:

- `DATABASE_URL` — the Transaction Pooler connection string (port 6543).
  Used by Prisma Client at runtime via `@prisma/adapter-pg`.
- `DIRECT_URL` — the Session Pooler connection string (same pooler host,
  port 5432). Used only by `npx prisma db pull` and any future
  `prisma migrate`/`db push` commands. (Not the dashboard's "Direct
  connection" string — see the IPv6 note above.)

Prisma's CLI does not auto-load `.env.local` (what the rest of this
project's scripts use via `node --env-file-if-exists`). Put these two
variables in a root `.env` file (gitignored, same as `.env.local`) —
`prisma.config.ts` loads it via `dotenv/config`.

## Verification

Run locally after setting `DATABASE_URL`/`DIRECT_URL` in a root `.env`:

```
npx prisma db pull      # read-only introspection, refreshes prisma/schema.prisma
npx prisma generate     # rebuilds the client into node_modules/@prisma/client
npm run typecheck
npm test
```
